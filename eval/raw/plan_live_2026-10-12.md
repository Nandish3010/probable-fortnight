# Live plan evidence (24 runs, deployed API)

Raw data: `plan_live_2026-10-12.json` (runs, summary, method). The file name carries 12 Oct per the
plan; the runs happened on 11 Oct 2026, 23:50 to 23:58 IST.

- Endpoint: `https://taal-agents-2obkp776ca-el.a.run.app`, model `gemini-3.5-flash`, backend
  `vertex`, re-plan deadline 90 s, no credentials, curl only.
- 24 runs: 12 on `gap_tea_ds04`, 12 on `gap_chips_ds07`, each with a fresh `X-Taal-Visitor:
  evid-<n>` header, at most 2 in flight, policy text unchanged.
- **22 of 24 model-planned** (`planner_source == "model"`, status `proposed`), **0 fallbacks**,
  1 loop iteration each. The 2 other runs (16 and 17) are not failures of the planner that we can
  see: their first poll returned 404 (run state is in process memory and a different, cold Cloud
  Run instance answered), so the outcome is unknown (they are not fallbacks) and they count as not passed. This is why `taal-agents` is capped at `--max-instances 1` (`infra/deploy.sh`).
- Planner elapsed over the 22 observed runs: **p50 26.5 s, p95 31.8 s**, min 20.4 s, max 33.3 s.
  Wall clock from POST to a finished poll: p50 29.8 s, p95 37.1 s.
- Two supplementary runs made afterwards with the same method (runs 25 and 26) were both
  model-planned (25.7 s and 30.1 s). They are kept in the JSON but not in the 22/24.

Caveat: one burst of 24 runs on one evening against a scale-to-zero service; a single dataset
(the seeded tenant), two gaps, same policy text. It shows the live path works repeatedly, not a
long-run reliability figure.
