# Customer prompt changelog

- v2 (2026-09-20): stock tools return an availability band instead of the on-hand count, and the prompt forbids stating a quantity. The first live Vertex run answered "Cola Zero 1L -- Qty: 127"; the stub had been worded around the rule since 32fda53 but the model was still handed the number.
- v1 (2026-09-12): initial. First-turn offer delivery from the tool only; stock-grounded substitution; STOP handling; JSON envelope output.
- v2 (2026-09-12): seventh tool `list_products` for browse and category questions; greeting only on whole words; JSON envelope unchanged.
- v3 (2026-09-12): reply in the customer's message language, not only their stored preference; "discount" recognised as an offer synonym with last-shown-product context; order confirmation names every line including a bundle partner added silently.
- v4 (2026-09-28): v3's script-matching instruction was live-verified not to hold: the per-turn note stated the stored preference as an ambient "writes in Kannada" fact, which outweighed the prompt's own rule and produced Kannada replies to English messages mid-conversation. The note now carries a pre-computed "reply in ___ for this turn" directive (agents.chat_runtime.detect_lang, the same deterministic function the stub backend already used) instead of the raw stored preference, with the proactive-first-turn-offer exception preserved (the offer text itself was pre-generated in the stored language at /approve time and must be delivered verbatim, not re-detected from the triggering message).
- v5 (2026-10-06): the order is what was offered, not what the model typed. Live, an `add:<sku>` click on the Masala Chips + Coconut Water bundle (Rs 58.5) was confirmed as "total is Rs 30": the model most likely sent only the clicked sku (and no or an invented play_id), so `place_order` priced one item at list. `place_order` now resolves the pending offer and builds the bundle itself, and returns the receipt text (`reply`), which the runtime shows verbatim; the prompt no longer asks the model to name lines or report a total. The receipt is in this turn's reply language (`detect_lang`, as the v4 directive), not the stored preference. An offer acceptance that `apply_offer` refuses (not treated, no consent, frequency cap, already redeemed) no longer falls back to a list-price order: `place_order` places nothing and returns the refusal, composed in code (`reply`), which the runtime shows instead of the model's text. An order with no offer context for its sku is unchanged. A redeemed offer counts as context only on the day it was redeemed (a repeat click); fixture 13 now expects the refusal.
- v6 (2026-10-09): `english_gloss` in the reply envelope. A Kannada reply carries one English line restating it, shown under the bubble. The runtime clamps it (280 characters, "English: " prefix), drops it if it names a number the reply does not, and falls back to a template built from the offer's structured fields; a tool-composed receipt or refusal gets the English twin of its own text from the tool.
- v7 (2026-10-10): reply language is enforced in code, not only requested. An `add:`/`cat:`/`no`/`stop` click keeps the stored language (it was read as English, so a Kannada customer got an English receipt); an English reply on a Kannada turn is replaced by the offer's Kannada wording (or a Kannada notice) with the English as the gloss; button labels for the known ids are composed in code, distinct per language; a dangling ")" and nested `(known: ...)` echoes are stripped. Prompt text unchanged.
